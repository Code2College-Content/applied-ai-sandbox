## Step 2 — CLAUDE.md behaviors

- **Run pytest after changes:** Without this reminder, Claude might ship code that fails tests and never realize it until user feedback.
- **Don't edit tests to make them pass:** Without this guardrail, Claude will absolutely "fix" failing tests by changing their assertions instead of fixing the actual code.
- **Read the task file first:** Without this convention, Claude invents requirements instead of reading what the tests actually expect.

## Step 3 — bad-context run

**Observations from "Add user login to this app." with no other context:**

- **Assumed:** I'd reach for Flask-Login + SQLAlchemy ORM and invent a `users` table with id/username/password, adding "user_id" foreign keys to the notes without asking if the data model should change.
- **Got wrong:** I'd overengineer features like "remember me" cookies, password reset, and email verification—none of which were requested—because they're standard auth patterns.
- **Asked (or didn't):** I wouldn't ask clarifying questions about scope, constraints, or whether notes should be per-user or shared, because I had no context warning me to stop and confirm requirements first.

## Step 4 — good-context plan

**Context brief with constraints, files, and acceptance criteria:**

```
I want to add a login flow to the sandbox app.

Goal: a user can register, log in, and log out. Logged-in users see
their own notes only.

Constraints:
- Use Flask-Login for session management.
- Passwords hashed with werkzeug.security — don't roll your own.
- Store users in a simple SQLite database (new db.py file); don't touch the in-memory notes approach for now.
- No "remember me" cookie, no password reset, no email — out of scope.

Files I expect to change:
- app.py (routes + login_manager wiring)
- db.py (new User model and database setup)
- templates/ (login.html, register.html, update home.html with logout link)

Acceptance:
- /register and /login render, /logout works.
- An anonymous visitor going to / is redirected to /login.
- Two users see two different notes lists.
- Existing tests still pass.

First: read the relevant files and propose a plan in plan mode. Don't write code yet.
```

**Claude's plan response with good context:**

1. **Add Flask-Login to requirements** (update requirements.txt)
   - Flask-Login is already specified in constraints; no decision needed.

2. **Create db.py with User model**
   - Simple SQLite setup (no migrations).
   - User table: `id`, `username` (unique), `password_hash`.
   - Password hashing: `werkzeug.security.generate_password_hash()` and `check_password_hash()`.
   - User class with `is_active`, `is_authenticated`, `is_anonymous`, `get_id()` (Flask-Login requirements).

3. **Update app.py**
   - Initialize `login_manager` and set `login_view = "login"`.
   - Move notes storage to per-user (dict keyed by user ID).
   - Update `/` (home) to require login and show only current user's notes.
   - Add `/register` (GET/POST) — render form, validate uniqueness, hash password, add to db, redirect to login.
   - Add `/login` (GET/POST) — render form, verify credentials, call `login_user()`, redirect to home.
   - Add `/logout` — call `logout_user()`, redirect to login.

4. **Update templates**
   - `login.html` — new file, simple form with username/password fields.
   - `register.html` — new file, form with username/password/confirm-password, link back to login.
   - `home.html` — add logout link in nav (only visible when logged in).

5. **Verify constraints are met**
   - No ORM bloat; simple `sqlite3` module.
   - No password reset, email, or remember-me.
   - Anonymous users redirected to `/login` automatically by Flask-Login.
   - Each user sees only their own notes.
   - Existing in-memory storage pattern stays for notes (just per-user now).

6. **Run tests** after each file to ensure nothing breaks.

## Step 5 — comparison

1. **Most-impactful line:** "No 'remember me' cookie, no password reset, no email — out of scope."
   - In bad-context, I assumed all three would be needed (standard auth patterns).
   - This single line cut feature creep and shaped the entire plan—it's why the good-context plan is focused instead of bloated.

2. **Line Claude ignored (or didn't clarify enough):** The brief doesn't specify error handling for registration failures.
   - What error message if username is already taken?
   - Should password validation rules be enforced (e.g., minimum length)?
   - Should there be a confirmation password field to prevent typos?
   - I assumed these details, but the brief should spell them out.

3. **Context I wish I'd included:** "Read the existing test suite first to understand what tests may break."
   - The brief mentions "Existing tests still pass" but doesn't clarify whether I should proactively read `tests/test_task_01.py` and `tests/test_task_02.py` before writing code.
   - This would prevent accidental breakage and surface unexpected interdependencies early.
   - Also: should clarify whether notes remain in-memory per-user forever, or is this a stepping stone to SQLite persistence later?
