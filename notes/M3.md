## Step 2 — CLAUDE.md behaviors
-It tells Claude to read the task and tests first, so Claude implements the exact required behavior instead of guessing what the app should do.
-It says not to edit files in tests/, which prevents Claude from “solving” the task by weakening or changing the spec instead of fixing the application code.
-It requires running pytest after changes, so Claude catches regressions and confirms both the new feature and earlier tasks still work before finishing.

## Step 3 - bad-context run
- Claude immediately assumed the app needed full authentication with users, passwords, sessions, and a database instead of first asking what “login” should mean for this tiny Flask project.
- It started modifying multiple files and introducing extra dependencies even though the existing app was intentionally simple and file-scoped.
- It guessed database models and routes that did not match the current project structure.

## Step 4 - good-context plan
What I'll read first

app.py — current routes, note storage, app factory pattern
templates/ — existing HTML to know what base layout exists
pyproject.toml / requirements.txt — confirm Flask-Login and werkzeug are available or need adding

Proposed changes
models.py (new file)

Import SQLAlchemy (or use raw sqlite3 if the project has no ORM)
Define a User model with id, username (unique), password_hash
Add set_password(raw) and check_password(raw) helpers using werkzeug.security.generate_password_hash / check_password_hash
Expose a db object and an init_db(app) function the factory can call

app.py

Initialize LoginManager, set login_view = "login"
Register @login_manager.user_loader that queries User by id
Add /register route — GET renders form, POST validates uniqueness, hashes password, writes row, redirects to /login
Add /login route — GET renders form, POST calls check_password, calls login_user(user), redirects to /
Add /logout route — calls logout_user(), redirects to /login
Decorate / with @login_required
Filter notes by current_user.id so each user sees only their own — notes dict becomes {user_id: [list]} or notes get a user_id field

templates/login.html

Minimal form: username, password, submit
Link to /register

templates/register.html

Minimal form: username, password, submit
Link to /login

templates/home.html (small update)

Add logout link in nav when current_user.is_authenticated

Notes schema strategy
Keep app.notes as a list of dicts but add a user_id key to each note. On the home route, filter: [n for n in app.notes if n["user_id"] == current_user.id]. No migration needed.
Acceptance check plan

Run existing pytest suite — should still be green before touching auth
Manually register two users, add a note as each, confirm isolation
Visit / logged out — confirm redirect to /login

What I won't do

No remember-me, no email, no password reset
No changes to the notes schema beyond adding user_id
No custom password hashing
