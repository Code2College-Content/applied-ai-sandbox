## Step 3 — bad-context run

_Prompt given verbatim in a fresh session: "Add user login to this app."_

- Assumed: kept users in-memory (an `app.users` dict of username→hash) to
  mirror the existing `app.notes` list, hashed with `werkzeug.security` (no
  new dependency), and seeded a hardcoded `admin` / `password` user — all
  decided on its own, never reaching for a database or Flask-Login.
- Got wrong: the delivered login gates nothing. The choice was that writing
  should require login, but after the test conflict it "held the gate," so
  login exists yet protects no route — a cosmetic, half-finished feature. It
  also over-built for a tiny sandbox (open-redirect guard, POST-only logout)
  and wrote its own `tests/test_login.py`, inventing the spec for an
  un-tasked feature.
- Asked: it did NOT just guess — it asked three targeted questions before
  coding (how much auth flow → login-only/seeded user; what requires login →
  writing only; how to handle the gate vs Task 01's tests → hold the gate).

**Takeaway for the Step 5 comparison:** this "bad-context" run behaved far
better than expected — it explored first, asked good questions, ran the test
baseline, and caught the Task-01 conflict before coding. The reason is that
the one-line prompt was *not* context-free: `CLAUDE.md` supplied the missing
context (in-memory storage, "plan first," "tests are the spec"). Ambient
project context can rescue an underspecified prompt, so the good-context
run's advantage is smaller than the exercise assumes.

## Step 4 — good-context plan

Plan proposed by Claude after reading the repo, adapted to what the sandbox
actually has (notes are an in-memory list, no DB, Flask-Login not installed).

**Goal:** A visitor can register, log in, and log out. Logged-in users see
only the notes they created.

**Reality vs. the brief (pushback):**
- Flask-Login is *not* an existing pattern — it's a new dependency to add to
  `requirements.txt` and the venv.
- `werkzeug.security` is available (ships with Flask) — fine for hashing.
- There is no notes schema or database; notes live in `app.notes` as
  `{title, body}`. Per-user notes requires adding an `owner` key, which
  unavoidably modifies how notes are stored — so "don't touch the notes
  schema" can't be honored literally.
- There is no `base.html`; templates are standalone, so nav links go inline
  rather than via a base template.
- "Anonymous `/` → `/login`" conflicts with "existing tests still pass":
  `@login_required` on `/` and `/notes/new` makes test_task_01 / test_task_02
  redirect (302) instead of 200, and `conftest.py` has no logged-in client.
  This must be resolved before coding.

**Files expected to change:**
- `app.py` — LoginManager + user_loader; routes `GET/POST /register`,
  `GET/POST /login`, `POST /logout`; stamp `owner` on new notes; filter
  home/new_note by `current_user`.
- `models.py` (new) — `User(UserMixin)`, `get_db()`, `init_db()`,
  `create_user`, `get_by_username`, `get_by_id`, using stdlib `sqlite3`.
- `templates/login.html`, `templates/register.html` (new, standalone).
- `templates/home.html` — inline login/logout/register nav links.
- `requirements.txt` — add `Flask-Login`.

**Acceptance:**
- `/register` and `/login` render; `/logout` works.
- Anonymous visitor to `/` is redirected to `/login`.
- Two users see two different notes lists (via the `owner` field).
- Existing tests still pass — *blocked on resolving the login/test conflict
  above* (log-in fixture or `LOGIN_DISABLED` under TESTING).

**Sequence:** deps → models.py + init_db → auth routes + loader → per-user
note filtering → templates + nav → resolve test/login conflict → `pytest`.
