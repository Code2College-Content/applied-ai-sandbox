## Feature I picked
- Add free-text search that filters the notes list by matching against title and body.

## Plan from chat
**Data model:** No changes — notes are already dicts with `title`, `body`, and `tags`.
Search operates at the view layer, not the storage layer.

**Route changes:**
- `GET /` accepts an optional `?q=` query param.
- If `q` is present and non-empty, filter `app.notes` to notes where `q` appears
  in `title` or `body` (case-insensitive).
- Pass `q` back to the template so the search box stays populated.

**UI changes:**
- Add a search bar above the notes list in `home.html`.
- Form uses `method="GET"` and `action="/"` so the query lives in the URL.
- Show a "X results for 'query'" line when a search is active.
- "Clear" link resets to `GET /`.

**Edge cases:**
- Empty `q` → show all notes (same as no param).
- No matches → show "No notes match your search" instead of blank list.
- Search and tag filter active simultaneously → apply both (AND logic).
- Whitespace-only query → treat as empty.

**Out of scope:** fuzzy matching, ranking by relevance, searching tags field.

## Review in chat
- One useful piece of feedback: The reviewer flagged that searching against `note["title"]` and `note["body"]` will crash with a `KeyError` if any note in the list is missing either key — notes created before the `tags` refactor might not have both fields normalized, so the fix is to use `.get("title", "")` and `.get("body", "")` instead of direct key access.

## Workflow retro

**The four lanes:**
Claude.ai chat handled the design phase — I described the feature in plain
English and got back a one-page plan with data model, route changes, UI
changes, and edge cases, all without writing a line of code. Claude Code did
the implementation: I handed it the chat plan wrapped in M3 constraints and
it produced both changed files in one pass. Copilot handled the two-minute
fit-and-finish work — docstring, variable rename — that would have been
overkill to brief an agent for. Chat did the final review: fresh eyes on the
diff caught the `.get()` bug that the implementing session couldn't see
because it was too close to its own output.

**Where one tool caught what another missed:**
The chat review caught the KeyError risk on notes missing title or body keys.
Claude Code never flagged it because it wrote the code and its context was
anchored to the happy path. A stateless reviewer with no investment in the
code found it in thirty seconds.

**What I'd change:**
I'd write the acceptance criteria before opening Claude Code, not after
pasting the chat plan. The constraints section felt bolted on — if I'd
written "must use .get() for dict access" as an explicit acceptance criterion,
the bug never would have shipped from the agent.

**Where I spent the most time as conductor:**
Translating the chat plan into a Claude Code brief. That handoff is where
the most judgment lives — deciding what to keep, what to tighten, what to
call out of scope. That was the right place to spend time. The tools are fast;
the thinking about what to ask them is where the work actually is.
