# M7 — Multi-Tool Workflows

## Feature I picked
- Like button that displays on posts.

## Plan from chat
New post_likes table with id, post_id (FK → posts), user_id (FK → users), and created_at. Unique index on (post_id, user_id) to prevent duplicates. Add a denormalized like_count integer (default 0) to the posts table, kept in sync via trigger or app layer.
Route changes

POST /posts/:id/likes — create a like. Auth required. Returns updated count and liked state.
DELETE /posts/:id/likes — remove a like. Auth required. Same response shape.
GET /posts/:id — extend response with like_count and viewer_has_liked (null if unauthenticated).
GET /posts (feed) — same additions on each post object in the list.


UI changes
Heart icon + count in the post action bar. Unfilled at rest, filled when liked. Optimistic toggle on click — revert on API error.

Edge cases

Double-like: the unique constraint is the hard stop; the UI should also debounce/disable the button mid-request.
Unlike a post the user never liked: return a 404 or no-op gracefully, don't error loudly.
Deleted post: cascade-delete its likes; no orphaned rows.
Deleted user: decide whether to soft-delete or hard-delete likes — like count should stay accurate.
Count drift: if the denormalized like_count drifts from actual rows (e.g. failed transaction), provide a reconciliation job or recompute on read as a fallback.
High concurrency: use atomic increments (UPDATE posts SET like_count = like_count + 1) not read-modify-write, to avoid race conditions.
